# GFD BI — собственная BI-платформа взамен Qlik Sense

**Дата:** 2026-08-07
**Статус:** дизайн утверждён, готов к планированию первого этапа

---

## 1. Зачем

Компания FMCG-дистрибуции анализирует данные ритейл-панели (scan data) в Qlik Sense.
Приложение «Scandata» читает PostgreSQL, перегружает данные к себе в память по
расписанию, и дальше 20–25 человек работают внутри Qlik.

Задача — заменить Qlik собственной платформой, которая:

- работает на живых данных, а не на выгрузке в память;
- держит 700 млн строк продаж и растёт на 20–23 млн строк в месяц;
- даёт конструктор отчётов и свободную выгрузку, а не только готовые листы;
- открывается по внутренней ссылке, как раньше открывался SSRS;
- развивается силами одного человека без обращения к вендору.

## 2. Что уже есть

**Сервер** `GFDDBScandata` (10.0.0.112), Ubuntu 24.04, **8 ядер, 62 ГБ RAM**.
Диски: `/` — 124 ГБ, `/mnt/gfd_data` (sdb) — 1 ТБ, свободно 611 ГБ.
Диск виртуальный, тип носителя по `ROTA` не определяется — скорость замеряется на первом прогоне.
Из софта: `python3`, `git`. ClickHouse, Docker, Node отсутствуют.
Доступ в интернет к репозиториям Ubuntu и `packages.clickhouse.com` открыт.
Сервер боевой, но с базой работает только один человек.

**PostgreSQL 16.14**, кластер в `/mnt/gfd_data/postgres/16/main`, база `gfd_database_scandata`.
Роли `gfd_admin` нет — подключение через `sudo -u postgres`.

Таблицы (схема `public`):

| Таблица | Назначение |
|---|---|
| `sales` | продажи: `store_no`, `xcode`, `pdate`, `salesitem`, `salesvalue`, `client`, `opt`, `name_file` |
| `product` | справочник товаров: `xcode`, `xname`, `brand`, `category`, `proizvod`, `litrag`, `pack`, `vkus`, `catlitrag` |
| `address` | точки продаж: `store_no`, `client`, `store_add`, `store_format`, `oblast`, `city`, `region` |
| `kib_monthly_data` | помесячный АКБ из внешнего источника (КИБ) |
| `load_log` | журнал загруженных файлов: путь, MD5-хеш, число строк |

Процедуры `calc_sales_opt()` и `update_opt_energy()` идентичны по телу и размечают
оптовые продажи флагом `opt`. Роль `bi_reader` имеет SELECT — под ней ходит Qlik.

**Текущий скрипт загрузки Qlik** фильтрует данные: `pdate >= 2023-01-01`,
`category <> 'прочее'`, исключает сети `ДОМ ЛЕНТА`, `КАРУСЕЛЬ`, `ЛЕНТА ЗООМАРКЕТ`,
`ПЯТЁРОЧКА РЦ`, переименовывает сети через `ClientMap` (9 правил), приводит
текстовые атрибуты к верхнему регистру. Блок КИБ генерирует фантомные строки
(по одной на точку) ради того, чтобы `Count(DISTINCT store_no)` давал АКБ.

## 3. Границы

**Делаем:** отдельную читающую витрину на ClickHouse, слой метрик, веб-приложение
с готовыми листами, конструктором и выгрузкой, синхронизацию с PostgreSQL.

**Не делаем:**

- не пишем в боевой PostgreSQL — только читаем;
- не меняем его настройки и не перезапускаем (это исключает потоковую репликацию);
- не переносим данные за пределы рабочего контура;
- не отключаем Qlik, пока цифры нового BI не сойдутся с ним;
- не делаем ролевую модель доступа к данным — все пользователи видят всё.

## 4. Архитектура

```
PostgreSQL (боевой)
      │  только чтение
      ▼
Синхронизатор ──► ClickHouse ◄── словари product / address / client_map
   (Python)            │           (перечитываются раз в минуту)
                       ▼
                 Слой метрик + HTTP API
                       │
                       ▼
                  Веб-приложение ──► nginx ──► http://gfd-bi/
                       │
              служебный PostgreSQL
          (учётки, сохранённые страницы)
```

**Синхронизатор** — отдельная программа. Три режима: залить кусок «месяц × сеть»,
сверить источник с витриной, залить всё заново в теневую таблицу с атомарной подменой.

**ClickHouse** хранит физически только продажи. Справочники подключены словарями
поверх PostgreSQL — правка в источнике видна в BI через минуту без перезаливки.

**Слой метрик** — единственное место, где формируется SQL. И готовые листы,
и конструктор, и выгрузка обращаются только к нему, поэтому одна и та же цифра
в разных местах интерфейса посчитана одним кодом.

**Служебный PostgreSQL** живёт в контейнере проекта. Боевая база не трогается.

## 6. Данные в ClickHouse

### 6.1 Что едет из PostgreSQL

Фильтры при заливке — **только стабильные правила**:

- исключение сетей `ДОМ ЛЕНТА`, `КАРУСЕЛЬ`, `ЛЕНТА ЗООМАРКЕТ`, `ПЯТЁРОЧКА РЦ`;
- отсечка по дате (на этапе тестирования — 2026 год; далее расширяется);
- связка с `product` по `xcode` — продажи без карточки товара не едут.

Фильтр по категории **не применяется**: везутся все категории, включая `прочее`,
пустые и `NULL`. Причина: категория активно правится в справочнике, и товар,
переехавший из «прочее» в «энергетики», должен появиться в отчётах без перезаливки.
Скрытие «прочего» — фильтр по умолчанию в интерфейсе, снимается галочкой.

Переименование сетей (`ClientMap`) и приведение к верхнему регистру выполняются
**не при загрузке, а в слое метрик** — через словарь, который правится без перезаливки.

### 6.2 Таблица продаж

Хранятся только факты. Типы ужимаются: `Date` вместо строки, словарные типы
для `client` и `xcode`, `UInt8` для флага опта вместо `varchar(5)`.
Исходный `id` из PostgreSQL сохраняется для сверки.

- **Партиционирование:** `(месяц, сеть)`. Данные приходят по сетям в разное время;
  такая нарезка позволяет подменить кусок «июль × Магнит», не трогая остальное.
  На всю историю получается порядка 500–600 партиций — для ClickHouse норма.
- **Сортировка внутри партиции:** по коду товара. Даёт сжатие и быструю выборку по товару.

Ожидаемый объём: 2026 год (~140 млн строк) — **2–3 ГБ**; полные 700 млн — **10–12 ГБ**.

### 6.3 Словари

`product` (по `xcode`), `address` (по паре `store_no` + `client`), `client_map`
(правила переименования сетей). Источник — PostgreSQL, перечитка раз в минуту.

Осознанный размен: фильтрация по бренду не использует первичный индекс и требует
чтения колонки кода товара (сотни мегабайт на 140 млн строк, доли секунды).
Взамен правки справочника видны через минуту без перезаливки продаж.

### 6.4 КИБ

В первый этап **не входит**. Фантомные строки не воспроизводятся: таблица агрегатов
поедет как есть, а деление АКБ между кодами товара будет выполняться в запросе.

### 6.5 Лимиты ClickHouse

Сервер делится с боевым PostgreSQL, поэтому:

| Параметр | Значение | Зачем |
|---|---|---|
| `max_server_memory_usage` | 40 ГБ | потолок, не резервирование; 22 ГБ запаса, чтобы системный OOM killer не убил PostgreSQL |
| `max_memory_usage` (запрос) | 10 ГБ | один пользователь не выжирает сервер |
| `max_threads` | 8 | интерактивные запросы используют все ядра, они короткие |
| `max_execution_time` | 60 с | кривой отчёт не висит вечно |
| фоновые слияния и заливка | прижаты | они длинные и лезут на тот же диск, где работает PostgreSQL |

Принцип: быстро для людей, скромно для фоновых задач. Тяжёлые операции — ночью.

## 7. Синхронизация

### 7.1 Заливка

Любой кусок заливается через промежуточную таблицу: читаем «месяц × сеть» из
PostgreSQL, пишем, **сверяем число строк и суммы с источником**, и только при
совпадении подменяем партицию одной атомарной операцией. Промежуточного состояния
пользователи не видят никогда, даже если процесс убить на середине.

Полная перезаливка идёт в теневую таблицу с обменом в конце — весь час работы
люди пользуются старыми данными и переключаются на новые мгновенно.

### 7.2 Обнаружение изменений

1. **По `load_log`** — новые файлы определяют затронутые пары «месяц × сеть».
2. **Сверка агрегатов** — число строк и суммы по каждой паре сравниваются между
   PostgreSQL и ClickHouse. Ловит любые изменения, включая правки руками и
   пересчёт процедурой `opt`.

Расписание:

| Когда | Что |
|---|---|
| каждые 10 минут | новые файлы + сверка последних трёх месяцев |
| ночью | полная сверка всей истории (тяжёлый запрос к PostgreSQL) |
| по кнопке | перезалить всё / перезалить кусок / только проверить |

Административные кнопки доступны только администратору. Полная перезаливка
предупреждает о нагрузке на боевой диск.

### 7.3 Поведение при сбоях

- PostgreSQL недоступен — повтор с нарастающей паузой, затем запись в журнал и красный флаг в админке;
- процесс упал на середине — боевая таблица не тронута, промежуточная выбрасывается;
- **цифры не сошлись — подмена не выполняется**, кусок остаётся прежним, в журнал пишется расхождение;
- каждый запуск журналируется: объём, длительность, результат.

Принцип: тихих поломок быть не должно. Лучше показать вчерашние данные, чем неверные.

## 8. Слой метрик

Меры и разрезы описываются декларативно, а не зашиваются в код.

### 8.1 Базовые меры

| Мера | Формула |
|---|---|
| Объём, шт | `sum(salesitem)` |
| Объём, л | `sum(salesitem × litrag)`, литраж из словаря |
| Продажи, ₽ | `sum(salesvalue)` |
| Средняя цена | продажи ÷ объём |
| **АКБ** | `uniq(store_no)` |

### 8.2 Правила АКБ

**Гранулярность — календарный месяц.** АКБ месяца — число уникальных точек,
где были продажи в этом месяце с учётом фильтров. Период из нескольких месяцев
даёт ряд значений; одно число за период — **среднее по месяцам**, не уникальные
за весь период.

Работает в любом разрезе — по бренду, сети, SKU, вкусу, литражу, производителю.

**АКБ не суммируется по строкам.** Точки, торгующие двумя брендами, попадут в оба
значения. Итоговая строка таблицы по таким мерам считается отдельным запросом,
а не сложением. Дистрибуция = АКБ разреза ÷ АКБ всей выборки.

### 8.3 Производные меры

Механизмы, а не отдельные формулы под каждый случай:

- **прирост год-к-году** — применим к любой мере;
- **доля** — вес разреза внутри выборки, применим к любой мере.

Три меры × три режима × любой разрез покрывают все пятнадцать вкладок текущего
Qlik и дают комбинации, которых там нет.

### 8.4 Разрезы

Время (год, квартал, месяц), товар (категория, бренд, производитель, вкус, литраж,
упаковка, SKU, `xcode`), точка (сеть, формат, область, город, `store_no`), флаг опта.

### 8.5 Фильтры по умолчанию

Скрытие категории «прочее» и пустых, исключение опта — задаются в конфиге,
снимаются в интерфейсе.

### 8.6 Кандидаты на второй этап

Взвешенная дистрибуция (точки взвешены по обороту), разложение прироста на
дистрибуцию и продажи с точки, выпадение товара из продаж, SKU на точку,
ценовой индекс к категории.

### 8.7 Сверка с Qlik

Перед запуском для пользователей меры сверяются с Qlik на одинаковых фильтрах.
Расхождение свыше 0,1% — блокер: пока цифры не сходятся, Qlik не отключается.
Точные выражения мер из Qlik переносятся в конфиг по мере получения.

## 9. Интерфейс

Решения проверены на интерактивном прототипе.

- **Фильтры — в левой панели**, сворачиваемой. Их девять, и горизонтальная
  раскладка Qlik съедает верхнюю четверть экрана.
- **Списки не закрываются** после выбора значения — можно отметить несколько подряд.
- **Поиск внутри фильтра** для длинных списков (брендов больше тысячи).
- **Период — два режима на переключателе:** «Диапазон» (с месяца по месяц, в том
  числе через границу года) и «Отбор» (галочки по годам и месяцам для сезонных
  сравнений). Плюс быстрые кнопки: 12 месяцев, с начала года, текущий год.
- **Вместо пятнадцати вкладок — три переключателя:** мера, режим, разрез.
- **Незакрытый месяц помечается визуально** — данные пришли не по всем сетям.
  В Qlik такой месяц выглядит как обвал продаж.
- **Тёмная тема по умолчанию**, светлая переключателем.
- **Личные страницы:** состояние фильтров сохраняется за пользователем.

## 10. Надёжность и тестирование

**Разработка ведётся локально на синтетических данных** — генератор создаёт
правдоподобный объём по реальной схеме. Данные из рабочего контура не выносятся.
Генератор позволяет проверять поведение на объёмах больше боевых.

Уровни проверки:

1. **Слой метрик** — на подготовленном наборе данных с заранее посчитанными
   ответами. Проверяются в первую очередь АКБ (несуммируемость, помесячная
   гранулярность), прирост год-к-году на границе года, доли.
2. **Синхронизатор** — обрыв на середине заливки, расхождение сверки, недоступность
   источника, повторный запуск после сбоя. Проверяется, что боевая таблица
   остаётся целой в каждом случае.
3. **API** — контракт запросов и отказ на некорректных параметрах.
4. **Нагрузка** — время ответа типовых запросов на полном объёме, до и после
   заливки, при параллельной работе нескольких пользователей.
5. **Сверка с Qlik** — по пункту 8.7.

## 11. Развёртывание и перенос

Разработка — на домашней машине, эксплуатация — на рабочем сервере.
Код едет через приватный репозиторий git; данные не едут ни в какую сторону.

**Секреты в репозиторий не попадают**: в git лежит только шаблон настроек,
реальные пароли вписываются на сервере в игнорируемый файл.

Установка на сервере: `git clone`, заполнить `.env`, `docker compose up -d`.
Обновление: `git pull` и перезапуск.

| Этап | Содержание | Критерий готовности |

Каждый этап получает свой план. Настоящий документ детализирует этап 1;
этапы 2–5 описаны рамочно и уточняются перед началом.

## 13. Открытые вопросы

1. **Глубина истории.** Тестирование — на 2026 годе. С какого года тянуть
   в эксплуатации: с 2023 (как в Qlik) или глубже — решается после замера скорости.
2. **Расхождение 2022 года.** В скрипте Qlik стоит отсечка `2023-01-01`, но на
   дашборде присутствуют данные 2022 года. Причина не установлена.
3. **Тип диска** под `/mnt/gfd_data` — замеряется на первом прогоне, от него
   зависит время полной перезаливки (оценка: от 20 минут до полутора часов).
4. **Доступ к GitHub** с рабочего сервера не проверен. Запасной путь — файлообменник.
5. **Точные выражения мер из Qlik** не получены. До их появления меры описываются
   по смыслу и сверяются по пункту 8.7.
6. **`/mnt/win_disk` недоступен** («Host is down»). Если исходные файлы загрузки
   лежат там, пайплайн наполнения PostgreSQL сейчас нерабочий — к проекту прямого
   отношения не имеет, но стоит проверить.
