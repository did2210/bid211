# Установка на сервер

Сервер `GFDDBScandata`, `10.0.0.112`, Ubuntu 24.04. Вход по ssh под `gfd_admin`.

Порядок такой: сначала разведка, потом установка. Разведка нужна, чтобы
не менять на боевой машине то, что и так уже настроено, и чтобы заранее
увидеть места, где придётся что-то решать.

**Что мы ставим:** только Docker. Всё остальное — ClickHouse и служебный
PostgreSQL — приезжает образами и живёт внутри.

**Чего мы не трогаем:** боевой PostgreSQL. Он остаётся где стоит, со своими
настройками и данными. От него нужен только сетевой доступ на чтение.

---

## Шаг 1. Разведка

Выполнить на сервере и сохранить вывод — по нему станет ясно, нужен ли
шаг с доступом к базе (пункт 3) и хватает ли места.

```bash
# что за система и сколько места
lsb_release -ds; uname -r
df -h / /mnt/gfd_data

# не стоит ли уже что-нибудь из нужного
which docker git python3 || true
docker --version 2>/dev/null || echo "docker отсутствует"

# заняты ли наши порты
ss -ltnp | grep -E ':(8123|9000|5433)\b' || echo "порты 8123, 9000, 5433 свободны"

# доступ к репозиториям
curl -sI https://download.docker.com | head -1
curl -sI https://github.com | head -1

# как боевой PostgreSQL пускает к себе
sudo -u postgres psql -tAc "SHOW listen_addresses"
sudo -u postgres psql -tAc "SHOW port"
sudo -u postgres psql -tAc "SELECT type, database, user_name, address, auth_method
                            FROM pg_hba_file_rules ORDER BY line_number"

# размер боевых данных — от него зависит время первой заливки
sudo -u postgres psql -d gfd_database_scandata -tAc "
  SELECT pg_size_pretty(pg_total_relation_size('sales')),
         count(*), min(pdate), max(pdate) FROM sales"

# как называются файлы загрузок — от этого зависит быстрый путь детектора
sudo -u postgres psql -d gfd_database_scandata -tAc "
  SELECT file_path FROM load_log ORDER BY loaded_at DESC LIMIT 10"

# как записаны имена сетей — фильтр сравнивает их как текст
sudo -u postgres psql -d gfd_database_scandata -tAc "
  SELECT DISTINCT upper(trim(client)) FROM sales ORDER BY 1"
```

Отдельно нужен пользователь для чтения. Роль `bi_reader` уже есть — под ней
ходит Qlik. Пароль от неё либо известен, либо заводим отдельную роль
(единственная запись, которую мы делаем в боевом кластере, и та — создание
роли только на чтение):

```sql
CREATE ROLE gfd_bi LOGIN PASSWORD 'придумать';
GRANT CONNECT ON DATABASE gfd_database_scandata TO gfd_bi;
GRANT USAGE ON SCHEMA public TO gfd_bi;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO gfd_bi;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO gfd_bi;
```

## Шаг 2. Docker

```bash
# ставим из официального репозитория: в репозитории Ubuntu версия старее
sudo apt-get update
sudo apt-get install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
     -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io \
     docker-buildx-plugin docker-compose-plugin
```

**Сразу перенести хранилище Docker на большой диск.** По умолчанию образы и
тома лягут в `/var/lib/docker` на корневой раздел, где 124 ГБ, — витрина его
забьёт вместе с боевой базой:

```bash
sudo systemctl stop docker
sudo mkdir -p /mnt/gfd_data/docker
echo '{ "data-root": "/mnt/gfd_data/docker" }' | sudo tee /etc/docker/daemon.json
sudo systemctl start docker
docker info | grep "Docker Root Dir"    # ждём /mnt/gfd_data/docker
```

Чтобы не набирать `sudo` на каждую команду:

```bash
sudo usermod -aG docker gfd_admin        # выйти и зайти заново
```

## Шаг 3. Доступ из контейнера в боевую базу

За справочниками ходит **сам ClickHouse**, из своего контейнера. Его
соединение придёт с адреса docker-сети (обычно `172.17.0.1` или `172.18.x.x`),
и боевой PostgreSQL должен такие подключения принимать.

Смотрим вывод `pg_hba_file_rules` из разведки:

- если там есть правило, покрывающее `172.16.0.0/12` или всю внутреннюю
  сеть, — **ничего делать не нужно**;
- если нет, потребуется одна строка в `pg_hba.conf`. Это единственное
  касание конфигурации боевой базы за весь проект, и оно **не требует
  перезапуска** — достаточно перечитать конфиг:

```conf
# доступ витрины BI: только чтение, только из docker-сети этого сервера
host    gfd_database_scandata    gfd_bi    172.16.0.0/12    scram-sha-256
```

```bash
sudo -u postgres psql -c "SELECT pg_reload_conf()"
```

## Шаг 4. Код и настройки

```bash
cd /mnt/gfd_data
git clone <адрес приватного репозитория> gfd-bi
cd gfd-bi
git checkout stage-1-data-foundation

# Каталоги под данные — рядом с репозиторием, но НЕ внутри него: в самом
# репозитории уже есть папки clickhouse/ и pg_app/ с конфигами и init-скриптом.
sudo mkdir -p /mnt/gfd_data/gfd-bi-data/clickhouse /mnt/gfd_data/gfd-bi-data/pg_app

cp .env.example .env
nano .env
```

Что вписать в `.env` на сервере:

| Переменная | Значение |
|---|---|
| `CH_PASSWORD` | придумать длинный |
| `PG_APP_PASSWORD` | придумать длинный |
| `PG_APP_DSN` | `postgresql://gfd_app:<пароль>@localhost:5433/gfd_app` |
| `PG_SOURCE_DSN` | `postgresql://gfd_bi:<пароль>@10.0.0.112:5432/gfd_database_scandata` |
| `DICT_SOURCE_HOST` | `172.17.0.1` — адрес хоста глазами контейнера |
| `DICT_SOURCE_PORT` | `5432` |
| `DICT_APP_HOST` | `pg_app` (имя сервиса, менять не нужно) |
| `LOAD_DATE_FROM` / `LOAD_DATE_TO` | глубина заливки; для первого прогона `2025-01-01` и `2026-07-01` |
| `ONLY_CHAINS` | для первого прогона `ПЯТЁРОЧКА,ПЕРЕКРЁСТОК` — заливаем две сети, а не миллиард строк |

Точный адрес хоста для словарей проверяется так:

```bash
ip -4 addr show docker0 | grep -oP '(?<=inet\s)\d+(\.\d+){3}'
```

## Шаг 5. Поднять и наполнить

```bash
docker compose -f docker-compose.yml -f docker-compose.server.yml up -d
docker compose ps                      # оба контейнера должны быть healthy

# синхронизатор запускается с хоста: python3 на сервере уже есть
cd sync
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"

.venv/bin/gfd-sync init                # таблицы, словари, журнал
.venv/bin/gfd-sync full-reload --yes   # первая полная заливка
.venv/bin/gfd-sync status
```

Первая заливка читает источник целиком — запускать вне рабочих часов.
На синтетике 11 млн строк это заняло 3,3 минуты; сколько выйдет на боевых,
покажет разведка из шага 1.

## Шаг 6. Проверка

```bash
cd /mnt/gfd_data/gfd-bi/sync

.venv/bin/gfd-sync verify --all        # ждём «Расхождений нет»
.venv/bin/pytest tests/test_performance.py -m slow -v   # замеры на витрине
```

**Обычный `pytest -q` на сервере запускать не нужно.** Тесты работают
в отдельной базе ClickHouse `gfd_test` и боевую витрину не трогают, но
часть из них обращается к источнику, а генератор синтетики начинается
с `DROP TABLE sales`. От случайного сноса боевой базы стоят два заслона:
роль `gfd_bi` умеет только читать, а сам генератор отказывается работать
с базой без метки `synthetic_data_marker`. Полагаться на них незачем —
проверять код надо дома, а на сервере гонять только замеры.

Числа замера записать в `docs/измерения.md` отдельным разделом — рядом
с домашними, для сравнения.
