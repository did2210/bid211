# Боевая база: что выяснили разведкой

Всё ниже снято с `gfd_database_scandata` на сервере `10.0.0.112` 2026-08-08.
Дешёвыми запросами — по системной статистике, без чтения самой таблицы.

## Объём

| | |
|---|---|
| Таблица `sales` | **335 ГБ** |
| Строк | **≈ 1 167 000 000** (оценка по `reltuples`, статистика от 2026-07-09) |
| Период | **2019-01-01 … 2026-06-01** (проверено по МАГНИТу) |
| Товаров в `product` | 43 260 |
| Сетей в `address` | 57 |

Для сравнения: синтетика, на которой всё разрабатывалось, — 12 млн строк.
Боевая база в **сто раз** больше.

## Данные помесячные

**`pdate` — всегда первое число месяца.** Продажи агрегированы по месяцам,
дней в базе нет. Генератор синтетики приведён к тому же виду; до этого он
раскидывал строки по дням, то есть проверялся на данных, которых не бывает.

Наша нарезка «месяц × сеть» ложится на это идеально: кусок — ровно одна дата.

## Имена сетей

**Регистр гуляет:** в `sales` встречаются и `ПЯТЁРОЧКА`, и `Пятёрочка`,
и `ВЕРНЫЙ`, и `Верный`. Наш `upper(trim(client))` это разбирает — хорошо,
что фильтр так и написан.

**Списки сошлись посимвольно.** Все четыре исключаемые сети присутствуют
ровно так, как записаны в коде, включая `ПЯТЁРОЧКА РЦ` с буквой «Ё».
Все девять правил переименования (`ЧИЖИК`, `СЛАТА`, `ХЛЕБСОЛЬ`, `БАТОН`,
`НАЛЕТУ`, `ВИНГАРАЖ`, `ТОЧКА ТАБАКА`, `НАША РАДУГА`, `ПЕРВЫЙ ВЫБОР В1`)
в базе есть.

Есть похожие, но отдельные сети, которые под наши фильтры не подпадают
и не должны: `ПЕРЕКРЁСТОК-ДЖЕМ`, `Я ЛЮБИМЫЙ ПЕРЕКРЁСТОК`, `ДИКСИ GO!`,
`ЛЕНТА ЭКОНОМ`, `ЛЕНТА ЗАМОРОЗКА`, `МАГНИТ АПТЕКА` и прочие. Сравнение
точное, так что они и не попадут.

## `load_log` устроен не так, как ожидал детектор

Записи выглядят так:

```
P:\vs code\linux_database\kib_file\энергет5.xls
P:\vs code\linux_database\kib_file\напитки 1.xls
```

Windows-пути к файлам КИБ, а не `СЕТЬ_ГГГГ_ММ.xlsx`. Значит быстрый путь
детектора (разбор имени файла ради сужения запроса) на боевых данных
не сработает и всё поедет медленным путём — полным сканом.

**Что с этим делать — открытый вопрос.** Похоже, определять затронутые куски
нужно иначе: не по имени файла, а по чему-то другому. Разбираться, когда
дойдём до расписания.

## Индексы: почему запросы шли полным сканом

В таблице семь индексов:

```
sales_pkey                 (id)
idx_sales_xcode            (xcode)
idx_sales_store_client     (store_no, client)
idx_sales_client_xcode     (client, xcode)
idx_sales_pdate_covering   (pdate) INCLUDE (salesvalue, client, store_no)
idx_sales_pdate_optimized  (pdate) INCLUDE (xcode, store_no, salesitem, client)
idx_sales_client_date      (upper(trim(client)), pdate) WHERE salesitem > 0
```

Наша заливка читает восемь колонок: `id`, `pdate`, `client`, `store_no`,
`xcode`, `salesitem`, `salesvalue`, `opt`.

- **`idx_sales_client_date` не подходит вовсе** — он частичный, построен
  только по строкам `salesitem > 0`. PostgreSQL берёт такой индекс, только
  если запрос гарантирует то же условие; у нас его нет и быть не должно
  (иначе потеряем строки с нулевым и отрицательным объёмом).
- **Покрывающие индексы по `pdate` не покрывают всё, что нужно:**
  в одном нет `salesvalue`, в другом — `xcode` и `salesitem`, а `id` и `opt`
  не входят ни в один. После индекса пришлось бы лезть в таблицу за каждой
  строкой — 17 млн случайных чтений на месяц.

Планировщик поэтому выбирал `Parallel Seq Scan` — и на выборку месяца одной
сети, и просто на выборку месяца:

```
Gather  (cost=1000.00..27144969.48 rows=86651 width=72)
  ->  Parallel Seq Scan on sales  (cost=0.00..27135304.38 rows=36105 width=72)
        Filter: (pdate >= '2026-01-01' AND pdate < '2026-02-01'
                 AND upper(trim(client)) = 'ПЯТЁРОЧКА')
```

То есть **каждый кусок «месяц × сеть» читал все 335 ГБ**, причём дважды:
один раз `COPY`, второй раз — подсчёт контрольных сумм. Тридцать шесть
кусков превратились бы в сутки, а сканы такого размера вымывают кеш страниц
у боевой базы, которой мы обещали не мешать.

## Индекс под синхронизацию

2026-08-08 Матвей запустил построение:

```sql
CREATE INDEX CONCURRENTLY idx_sales_bi_sync
  ON public.sales (pdate, upper(trim(client)));
```

`CONCURRENTLY` — без блокировки таблицы, Qlik продолжает работать.
Ожидаемый размер — порядка 30–40 ГБ при 611 свободных.

Это единственное изменение боевой базы за весь проект, сделано с ведома
и по решению Матвея. Данные оно не трогает.

**После построения обязательно:**

```sql
ANALYZE public.sales;
```

Без этого статистика по выражению `upper(trim(client))` не соберётся, и
планировщик может по инерции остаться на полном скане. Проверять планом
запроса, а не на глаз.

## Доступ

- Роль `gfd_bi` — только чтение (`SELECT` на все таблицы `public` плюс
  права по умолчанию на будущие). Пароль на сервере в `~/gfd_bi_pass.txt`.
- В `pg_hba.conf` добавлена строка для docker-сети витрины:
  `host gfd_database_scandata gfd_bi 172.30.0.0/24 scram-sha-256`.
  Применена через `pg_reload_conf()`, без перезапуска.
- Проверено делом: ClickHouse из контейнера прочитал справочник товаров —
  словарь `dict_product` загрузился и отдал 43 260 позиций.
